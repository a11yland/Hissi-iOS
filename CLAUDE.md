# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Run

```bash
# One-time: the API token lives in a gitignored file (empty stub is enough to build)
cp Secrets.example.swift Shared/Secrets.swift

# Build for simulator
xcodebuild -project Hissi.xcodeproj -scheme Hissi \
  -destination 'platform=iOS Simulator,name=iPhone 17' build

# List available simulators if the above fails
xcrun simctl list devices available | grep iPhone

# Run unit tests (SwiftPM, runs on macOS)
swift test --package-path HissiTests
```

Unit tests live in `HissiTests/` as a standalone Swift Package (`HissiCore`, whose source directory is a symlink to `Shared/`) with JSON API fixtures in `HissiTests/Tests/Fixtures/`. CI runs them on pushes to `main` and on PRs that touch the iOS sources (`.github/workflows/ios.yml`, which copies the Secrets stub first); the app itself is built and archived by Xcode Cloud (`ci_scripts/ci_post_clone.sh` writes `Shared/Secrets.swift` from the `ACCESSIBILITY_CLOUD_APP_TOKEN` environment variable). A weekly `seed-drift` workflow regenerates the seed catalog (API credentials from repo secrets) and diffs it against the bundled one via `scripts/diff-seed-catalog.py`, filing a `seed-drift` issue on divergence — the seed itself is still regenerated manually per release. No linter is configured.

## Architecture

Swift/SwiftUI app (iOS 18+ / watchOS 10+, plus a **Mac Catalyst** build of the iOS app — `SUPPORTS_MACCATALYST` on `Hissi` and `HissiWidget`, which also makes it an iPad app, `TARGETED_DEVICE_FAMILY = 1,2`; the Mac gets no Live Activity and no watch: ActivityKit and WatchConnectivity are unavailable there, so `LiveActivityController` and `WatchSync` carry a `#if !targetEnvironment(macCatalyst)` stub, the `Shared/` ActivityKit guards include the same condition, the Live Activity is left out of the widget bundle and "Embed Watch Content" is filtered to iOS via `platformFilters`; `SUPPORTED_PLATFORMS` stays `iphoneos iphonesimulator` — adding `macosx` offers a *native* macOS build next to Catalyst, and Xcode Cloud's "Archive - macOS" action (`generic/platform=macOS`, no variant) then picks that one and dies on UIKit; verify with `xcodebuild -scheme Hissi -destination 'generic/platform=macOS' archive`) that monitors user-selected elevators via the [transit.accessibility.cloud](https://transit.accessibility.cloud) API (a Payload CMS: flat Elevators/StatusSpans/StopPlaces collections, joined locally by id — the elevator's own `operational_status` is the live status, spans supply disruption text/date; endpoints and fields verified live) and shows their live status across four targets: `Hissi` (iOS app), `HissiWidget` (iOS widget extension), `HissiWatch` (watchOS app) and `HissiWatchWidget` (watchOS widget extension for complications).

Each of the four target folders carries a `PrivacyInfo.xcprivacy` (picked up as a bundle resource automatically) declaring the `UserDefaults` required-reason API (`CA92.1`, `1C8F.1` for the App Group suite) — App Store Connect rejects uploads without it; a new required-reason API (file timestamps, system uptime, disk space, keyboards) has to be added to all four.

The project uses `PBXFileSystemSynchronizedRootGroup` — **any `.swift` file added to `Hissi/`, `HissiWidget/`, `HissiWatch/`, `HissiWatchWidget/` or `Shared/` is automatically compiled** into the corresponding target(s) without touching the `.xcodeproj`. `Shared/` is wired into all four targets, so code dropped there is available everywhere.

See [`docs/architecture.md`](docs/architecture.md) for a data-flow diagram.

**Colours**: the palette ("Creme-Lila", from the design package) is the set of named colour pairs in `Shared/Colors.xcassets`, exposed as `Color.hissi…` statics in `Shared/HissiColors.swift` and compiled into all four targets. `HissiBackground` (cream `#FBF3E4` / deep purple `#120E17`) is the ground of every screen — Lists drop the system canvas via `hissiList()` and paint their rows on `HissiSurface` with `HissiSeparator` lines via `hissiRows()`; secondary text uses `HissiTextSecondary`. The tint is the `AccentColor` pair (light `#503C74`, dark `#D4BBFC`; `ASSETCATALOG_COMPILER_GLOBAL_ACCENT_COLOR_NAME` on each target, so the Live Activity's button gets it too) — the design's lighter `#69548D` is 5.9:1 on cream, so the tint is the palette's button lilac instead, which keeps it WCAG AAA (7:1) as text on every ground it is drawn on; `PaletteTests` reads the colorsets and checks it, plus the network badge colours in `Shared/Palette.swift` (`WCAGContrast` does the maths). `.borderedProminent` labels take `HissiOnButton` (`prominentButtonLabel()`, app-only) — white on the pale dark tint would be 1.7:1. Status colours follow the mark — ping green / amber / red, each as a symbol colour (`ElevatorStatus.symbolColor`) and a darker text variant (`textColor`, AA on every ground, also tested); the status *shapes* are the icon's system too (`ElevatorStatus.symbolName`: circle with check, square with question mark, cross). The favorite star and the map pin are lilac, never yellow or red, because those mean "unbekannt" and "gestört" here. The two watch targets spell the dark status values out as constants (the face never switches to light).

**Localization**: German (source) and English via `Shared/Localizable.xcstrings`, shared by all four targets. The German literals in code double as the localization keys — SwiftUI `Text` literals localize automatically, `String`-building code goes through `String(localized:)`. The language switch is iOS's per-app setting (no in-app toggle; widgets/complications follow the system). accessibility.cloud requests carry only the app's language with server-side German fallback (`AccessibilityCloudClient.requestLocale`); `Lenient.localizedText` still resolves full localization maps as a hedge. The SwiftPM test package has no catalog, so `String(localized:)` falls back to the German keys there — tests assert German strings.

### Source of truth

The **iOS app is the only place favorites are created and managed** (via search) — on the iPhone, and as the same app on iPad and Mac, which share them through iCloud (below). The widget, watch app and complications are read-only mirrors. Favorites are stored in `Shared/FavoritesStore.swift` (App Group `UserDefaults`, suite `group.com.a11yland.Hissi`, key `favoriteElevators`); the list starts empty. The **stored array is the displayed order** — sorting happens once when writing (`Shared/FavoritesOrdering.swift`, pure and unit-tested), so every mirror renders it as it stands. Default is `FavoritesOrder.recentlyAdded` (newest first, keyed on `MonitoredElevator.addedAt`; a new favorite is prepended); dragging a row in the iOS list switches to `.manual` and persists that order verbatim, and the sort section of the overflow menu switches back. Favorites stored before `addedAt` existed are stamped once from their append order (`backfillAddedAtIfNeeded`), which flips such a list into newest-first on upgrade. **iCloud mirror**: the iOS app also mirrors the favorites (membership, order, sort mode — statuses stripped, `FavoritesCloudSnapshot`) into iCloud's key-value store (`Hissi/Services/FavoritesCloudSync.swift`, entitlement `com.apple.developer.ubiquity-kvstore-identifier` in `Hissi.entitlements`, **pinned** to `$(TeamIdentifierPrefix)com.a11yland.LiftBoy` rather than `$(CFBundleIdentifier)`: a successor app from the same team under a new bundle id keeps that value and imports the LiftBoy favorites on first launch — never change it), so they survive a reinstall and follow the user to another iPhone/iPad/Mac (FR4a); without iCloud nothing changes. The watch is not an iCloud participant — it still gets the favorites from its paired iPhone via `WatchSync`. The App Group store stays what every target reads. Merge rules are pure in `Shared/FavoritesCloudMerge.swift` (unit-tested): an installation that has never synced (local flag in standard defaults — a reinstall erases it) or hears an initial-sync/account change **unites** both lists; afterwards the cloud copy from another device is **adopted** (last writer wins, so removals propagate). Every local change uploads via `ElevatorMonitorService.fanOut()` (skipped when iCloud already holds the same snapshot, so status refreshes never write); `start()` runs in the service's `init` after the one-time migrations and before the first read. **Export** (FR4b): a `ShareLink` in the favorites footer hands out the favorites as a dated JSON file (`Shared/FavoritesExport.swift` — versioned contract `com.a11yland.liftboy.favorites` v1, statuses stripped via `MonitoredElevator.withoutStatus`, ISO 8601 dates, unit-tested; `Hissi/Services/FavoritesExportFile.swift` is the `Transferable`). Export-only — nothing in Hissi reads the file back; the format is a documented contract for a successor app (field list in `Shared/FavoritesExport.swift`). Fields are only ever added; a breaking change bumps `currentVersion`.

### Data flow

1. **Search** (iOS only): a bottom search field in `ContentView` drives `SearchService`, which filters the equipment catalog by station name. Name search happens locally and **two-phase** (`SearchService`): phase 1 renders instantly from `EquipmentCatalog.snapshot()` — the in-memory or **disk-persisted** catalog (App Group container so the widget extension reads it too, live join + fetch time, seed overlay applied on load) of any age, kicking off the shared rebuild when stale; phase 2 awaits that rebuild (`searchStations` → `all()`, cold ~30 s of pure server time thanks to speculative pagination — the remembered per-collection `totalPages` lets all expected pages go out alongside page 1) and re-renders with live statuses (a subtle "Status wird aktualisiert …" list banner marks the wait, so a stale snapshot never looks final) — stale results beat an error screen, the error only shows when there is nothing at all. On the very first launch (no snapshot yet) the bundled seed previews names instead of a spinner — fully favoritable: a favorite created from a seed record's id resolves from the seed (status unknown) until a catalog knows its live counterpart, then bridges to it via the operator inventory number (`EquipmentCatalog.bridgedLiveIds`, pure) and adopts the live numeric id (`StatusMerge`; the app persists the migration via `FavoritesStore.migrateIds` on the next refresh). `Shared/EquipmentCatalog.swift` (an actor, 10-min TTL, concurrent callers share one in-flight build; TTL/cache path/build injectable, persistence unit-tested) fetches the catalog once via `AccessibilityCloudClient.fetchCatalog()` — the three transit.accessibility.cloud lists (Elevators, StatusSpans, StopPlaces) paginated in parallel with `depth=0` (StatusSpans filtered to active ones — the full collection is history), joined by numeric id (`join`, pure; the elevator's own `operational_status` decides, the current span adds disruption text and status-change date, unknown stays unknown — never a false "working") — and matches against the joined station names. The live fetch is overlaid (`EquipmentCatalog.overlaid`, pure) with the **bundled seed catalog** (`Shared/Resources/seed-catalog.json`, regenerated per release by `scripts/generate-seed-catalog.py`): live records match seed records via the operator inventory number (`linked_data.operator_inventory_id` = the seed's `fastaEquipmentNumber`), and the seed backfills what the API doesn't serve — source/operator names (only feed ids at `depth=0`), coordinates (none at all) and region. Station names it no longer adds in practice: every live record the seed matches already carries a stop-place link (verified 2026-09-27: 609 of 3180 elevators are linked, all 526 seed matches among them; the other 2571 carry no station reference at all — DB inventory numbers, descriptions like "→ Gleis 1" — and stay invisible, because search matches on the station name; whether any of them lie in VBB territory is unknown, the platform itself doesn't know their station). What the number leaves unanswered — ~30 seed numbers went stale upstream (e.g. U Spittelmarkt), and most live records have no seed counterpart at all — falls back to the **station** (`EquipmentCatalog.stationBackfilled`/`stationKey`, pure): the seed records whose station name matches once the network prefix is folded away ("U Spittelmarkt (Berlin)" = the stop place's "Spittelmarkt (Berlin)") supply coordinates and region, and source/operator only when they all name the same one — otherwise those rows stay empty rather than claiming the wrong operator. Live always wins; the inventory number is never taken from a sibling (it identifies the elevator, not the station). Seed records the live catalog doesn't answer for are appended status-unknown — `fasta` records missing upstream, `brokenlifts` records while their whole station is absent (currently only S Fredersdorf, reported upstream), or the whole seed when offline. Results are grouped by `SearchGrouping` (pure, unit-tested): **region → station → network**. Region (Berlin/Brandenburg, section headers only when both are present) comes from the AGS prefix of the StopPlace's DHID (`de:11…`/`de:12…`), the seed's `region` field, or a name heuristic (`TransitRegion`). Stations merge across sources by name; inside a station, `TransitNetwork.classify` splits elevators into U-Bahn/S-Bahn/Regionalverkehr subsections (subheaders only at multi-network stations) — the BVG feed carries U- **and** S-platform elevators at S+U stations (e.g. Pankow), so the description decides; unmarked street/mezzanine elevators land in a "Zugang" bucket. The stop place's transport modes (`modes.servicedTransportModes`: 1 = S-Bahn, 2 = U-Bahn, 3 = Regional-/Fernbahn → `Equipment.stationNetworks`) settle what neither feed nor name carries — DB records at unprefixed S-Bahn stations (Waßmannsdorf) and unmarked elevators at single-network stations; seed-only records carry no modes, so offline the old name fallbacks (and their Regionalverkehr limitation) remain. Rendered by `SearchResultsList` with an inline favorite star per elevator (`FavoritesStore.add/remove`). Opening a result's detail (`ElevatorDetailView`) does not wait for phase 2: for a non-favorite it runs one targeted `EquipmentCatalog.equipment(for:)` request on appear (the favorites' refresh path, free while the catalog cache is fresh), shows the `StatusMerge` result itself and hands it back to the list via `SearchService.apply` → `SearchGrouping.replacing` (pure, unit-tested), so row and detail agree — favorites skip this, the service refreshes them.
2. **Fetch & parse**: `Shared/ElevatorRefresher.swift` `refreshAll()` (status source injectable via `StatusSources` — the orchestration is unit-tested with a stub) resolves **all** favorites in **one targeted request** (`EquipmentCatalog.equipment(for:)` → `AccessibilityCloudClient.fetchEquipment`: `where[id][in]` over the numeric favorite ids, `depth=1` + `populate` resolve the current status span inline — never one request per favorite, and no full catalog build; a still-fresh catalog cache — in-memory or freshly persisted — answers for free; non-numeric seed-record favorites bridge to their live records via the operator inventory number as soon as any cached catalog knows them — the favorite then adopts the live id, persisted via `FavoritesStore.migrateIds` — and resolve from the bundled seed status-unknown until then). The full catalog build stays search-only. transit.accessibility.cloud is the **only** status source: the platform ingests the operator feeds (incl. DB FaSta, ~2-minütlich) itself, so the former FaSta override and brokenlifts.org scraping are gone. `StatusMerge.apply` (Shared, pure) folds a catalog record into a favorite. On failure an elevator keeps its previous values and its id is reported back. **Pre-migration favorites are not mapped**: favorites stored under an old id scheme (old `www.accessibility.cloud` `_id`, `fasta-…` or `brokenlifts-…` seed id — anything non-numeric) are deleted once by `FavoritesStore.removeLegacyFavoritesIfNeeded` (flag-guarded, iOS app only — it owns the favorites), and the favorites area shows a dismissible DE/EN notice (`removalNoticePending`) asking users to re-add via search.
3. **Timestamps**: `lastChecked` = when the app last polled (`Date()` at fetch); `lastUpdated` = the source's own `lastUpdate` (how fresh the status is at accessibility.cloud). They are distinct — a fresh poll can still return stale source data. All favorites are polled together, so "checked" is **global**: shown once per list (iOS favorites footer, watch list footer) as the max `lastChecked`. Per-elevator views (rows, iOS/watch detail) show `lastUpdated` ("Stand …" / "Datenstand") only.
4. **Cache**: `ElevatorMonitorService` persists the latest state via `Shared/ElevatorCache.swift` to the same App Group (key `cachedMonitoredElevators`) so it is shared with the widget and survives restarts.
5. **Refresh cadence**: `ContentView` refreshes on appear, then every `RefreshInterval.minutes` (30) via `Task.sleep`, on `scenePhase → .active`, on pull-to-refresh, and via a refresh button in the top-trailing toolbar. On `scenePhase → .background` it also schedules a `BGAppRefreshTask` (`BackgroundRefreshManager`, iOS-only, id `com.a11yland.Hissi.refresh`): the handler re-fetches the favorites off `ElevatorRefresher.refreshAll`, updates `ElevatorCache`, reloads widget timelines and pushes to the watch, so the widget/complications stay fresh between foreground sessions. The task id and `UIBackgroundModes` (`fetch`) live in `Hissi/Info.plist` (a partial plist merged into the generated one; the file is excluded from the target's synchronized resources via a membership exception). While a Live Activity ("Live-Status") runs, both cadences tighten to `RefreshInterval.liveStatusMinutes` (10) — the foreground poll off `LiveActivityController.isRunning`, the background scheduler off the App-Group flag `LiveStatusFlag` (nonisolated, so the scheduler needs neither ActivityKit nor the main actor).
6. **Watch sync**: after each refresh and on every favorite toggle the iOS app pushes the favorites to the watch via `WatchSync` (WatchConnectivity `updateApplicationContext`).

`ContentView` is a single screen (no tabs): a persistent bottom search field (`.searchable` with an `isPresented` binding, so a "Stationen in der Nähe anzeigen" button — in the empty favorites state, and as a row between the live-status section and the favorites list — can open it and kick off the location fix), above which the area shows the **favorites** by default, **recent searches** (`RecentSearchesStore`, capsule chips) plus **nearby stations** while the field is focused and empty, or **search results** while a query is present. Nearby: `LocationProvider` (Shared — the watch uses it too; one-shot when-in-use fix, prompt only from the user's button tap; usage strings in `Hissi/Info.plist` + `InfoPlist.xcstrings` and, for the watch, the `INFOPLIST_KEY_NSLocationWhenInUseUsageDescription` build setting + `HissiWatch/InfoPlist.xcstrings`) feeds `NearbyStations.nearest` (Shared, pure haversine sort over the catalog snapshot's seed-backfilled coordinates, unit-tested) — on-device only, never stored. Nearby means **within walking distance** (`NearbyStations.walkingRadiusMeters`, 1 km): a station beyond that stays out even when it is the closest one, the header names the radius ("bis 1 km zu Fuß") and an empty result says "Keine Station mit Aufzug im Umkreis von 1 km" rather than listing a car ride away. Each row carries the station's **lift status** next to the distance, rolled up over *all* its elevators (an elevator without coordinates can't place the station but still counts) with the same precedence as everywhere else — broken > unknown > all-clear, and never an all-clear while something is unknown; the label gives the ratio ("1 von 3 außer Betrieb") as soon as a station has more than one lift, a single-lift station speaks `ElevatorStatus.label`. Statuses load **two-phase** like the search: the snapshot renders instantly (stale, or status-unknown from the seed on first launch), then one targeted request over exactly the shown stations' elevators (`EquipmentCatalog.equipment(for:)` — free while the catalog cache is fresh) re-states the rows via `NearbyStations.restated` (pure: only statuses change, names/distances/order never — a landing refresh must not reshuffle rows under the user's finger, which is also why the sort stays distance-only and ignores status). Elevators the refresh doesn't answer for keep their previous status, and a failed refresh leaves the rows standing — nearby is a suggestion, not a core flow. On first launch it presents a welcome sheet, and once per release **with curated notes** a "Was ist neu" sheet (`WelcomeGate` in Shared decides, pure and unit-tested; `OnboardingState` persists to standard defaults; note content lives in `WhatsNewSheet` — new releases add their version to `WelcomeGate.curatedVersions` **and** a case in `WhatsNewSheet.notes`, silent otherwise; 1.0 has none, the welcome sheet carries the app's features via `AppFeature.welcome`). The top-leading logo is a button that presents `AboutSheet` ("Über Hissi"): a sectioned `List` with a "Fertig" toolbar button rather than the onboarding scaffold, so nothing hides below the fold — header (icon, name, tagline), the `AppFeature.all` rows (five one-sentence features; the welcome sheet draws its three from the same list), the data attribution naming accessibility.cloud and Sozialhelden e.V. as link rows (`AttributionLinks`; the favorites footer carries the same two links), a privacy note (no account, no data collection) and the version as a row. The top-trailing toolbar holds a sort menu (`arrow.up.arrow.down`, favorites mode with more than one favorite: the `FavoritesOrder` picker as a state display, not an overflow menu — sorting belongs to the list it sorts), a refresh button (favorites mode only) and a light/dark toggle (`AppAppearance` in `@State`, applied with `preferredColorScheme`). Reordering needs nothing set first — a row is dragged directly (`ForEach.onMove`, no `EditMode`); a grip glyph in each favorite row is the only hint that it can be (`ElevatorRowView.showsReorderHandle`, decorative and `accessibilityHidden` — the drag starts anywhere on the row), and the drag itself is what switches the order to `.manual`; the same move is offered per row as VoiceOver/Switch-Control actions ("Nach oben/unten bewegen"), which a drag gesture doesn't reach. The toggle is session-only and resets to the system setting on every cold start. The search field is debounced via `.task(id: query)`; favorite toggles and refresh failures emit `.sensoryFeedback`.

### App Shortcuts (`Hissi/Intents/`)

Three **presets** — shortcuts that appear in the Shortcuts app, Spotlight and Siri on their own, without the user assembling anything. App-target only (**not** `Shared/`, which would compile them into all four targets); exactly one `AppShortcutsProvider` (`HissiShortcuts`) may exist per app, and its declaration order is the listing order.

| Shortcut | Intent | Runs |
|---|---|---|
| „Aufzugstatus prüfen" | `CheckElevatorsIntent` | in background, speaks `ElevatorSummary.label` |
| „⟨Aufzug⟩ prüfen" | `CheckElevatorIntent` | in background, speaks one elevator's status |
| „Favoriten öffnen" | `OpenFavoritesIntent` | opens the app (`openAppWhenRun`) |

Both status intents go through `IntentRefresh.refreshedFavorites()`: refresh **all** favorites (one targeted request answers them all anyway), fan the result out via `RefreshFanOut.distribute` (cache, widget timelines, watch push, live-status update — the one shared post-refresh fan-out; the app's refresh, the favorite toggle and the background task use the same) — a Shortcut run is a refresh like any other — and only then report on what was asked. `ElevatorSummary` is what the aggregate shortcut speaks, so the Shortcuts answer and every glanceable surface stay one vocabulary. `CheckElevatorIntent` also returns its `ElevatorEntity` (`ReturnsValue`), and on iOS 26.4+ the entity travels across apps as a **place**: a `Transferable` conformance exports a GeoToolbox `PlaceDescriptor` from the seed-backfilled station coordinates (export-only — nothing imports an elevator, FR4; no coordinates → no place rather than a wrong one), so a Shortcut can chain "⟨Aufzug⟩ prüfen" into directions or a message.

The parameterized shortcut is built by the system from `ElevatorEntityQuery.suggestedEntities()` — one phrase per favorite. Two consequences: without `suggestedEntities()` there are **no** parameterized shortcuts at all, and the favorites have to be re-published via `HissiShortcuts.updateAppShortcutParameters()` on every launch (`HissiApp.init`) **and** on every favorite toggle (`ElevatorMonitorService.toggleFavorite`, next to the widget reload). `ElevatorEntity` is a projection of `FavoritesStore`, never a second source of truth (FR4).

**Localization is split**: every phrase must contain `\(.applicationName)`, and those phrases are extracted into a *separate* catalog `Hissi/AppShortcuts.xcstrings` — recognized by file name, app-target only. Titles, parameter titles, descriptions and dialogs stay in `Shared/Localizable.xcstrings`.

All three intents also adopt **`PredictableIntent`**: `predictionConfiguration` supplies the wording the system uses where it *proposes* an action (Siri Suggestions, Spotlight) rather than where the user picks one. The parameterized one fills the station in — "S+U Pankow prüfen" is actionable, "Aufzug prüfen" is not. This targets the proactive surfaces, **not** the widget gallery, whose ordering has no API at all. Descriptions alone predict nothing, so `ElevatorMonitorService.refreshRequestedByUser()` donates `CheckElevatorsIntent` — wired to pull-to-refresh and the toolbar button only. The on-appear load, the 30-minute poll and the foreground refresh happen whether or not anyone wanted them; donating those would teach a pattern the user never expressed.

### Widget (`HissiWidget/`)

Separate Xcode target (Widget Extension), wired up in the `.xcodeproj` and embedded into the iOS app at build time. Sources auto-sync from `HissiWidget/` plus `Shared/`. Reads the favorites directly (same App Group as the app), fetches live status itself, and falls back to `ElevatorCache` on request failure. The app reloads the widget timelines on every refresh and favorite toggle (`RefreshFanOut`, `reloadAllTimelines` covers every kind) — cheap, because a cache written within `RefreshInterval.cacheReuseSeconds` (90 s) answers a reload without a fetch; that also keeps the two kinds from fetching once each. Refresh interval driven by `RefreshInterval.minutes`.

`@main` is a **`WidgetBundle`** (`HissiWidgetBundle`) holding three widgets plus the Live Activity (`LiveStatusActivity`, see below — not a gallery tile, so its position in the bundle is irrelevant) — the declaration order is the order the gallery lists the *widgets* under the app, hero first:

1. **`HissiWidget`** (kind `HissiWidget`, "Aufzug-Status") — `systemSmall` (broken/unknown count, "Alle in Betrieb", or an explicit no-favorites state — never a false all-clear) and `systemMedium` (per-elevator list, broken first, capped at 3 rows + "+ n weitere", under the same mark-plus-verdict header the large family has) on the home screen / in StandBy, plus `accessoryCircular`, `accessoryRectangular` and `accessoryInline` on the **lock screen**.
2. **`HissiFavoritesWidget`** (kind `HissiFavoritesWidget`, "Alle Favoriten") — `systemLarge` only: the same list capped at 8 rows, with the aggregate verdict as a header. A separate widget rather than another family on the first one **on purpose**: the gallery lists widget *kinds*, so folding `systemLarge` in would have added a size option nobody browsing the gallery ever sees.
3. **`NearbyWidget`** (kind `HissiNearbyWidget`, "In der Nähe", `HissiWidget/NearbyWidget.swift`) — `systemSmall` (nearest station), `systemMedium` (3 rows) and `systemLarge` (8 rows): the stations within walking distance and their lift status, the app's nearby block as a tile. **Location in the extension**: `NSWidgetWantsLocation` in `HissiWidget/Info.plist`; the system extends the app's when-in-use authorization to the widget when the user adds it, `CLLocationManager.isAuthorizedForWidgetUpdates` says whether it did (else "Standort in der App erlauben"), and a fix is only delivered for a while after the widget was last visible (else "Standort nicht verfügbar"). One fix per timeline with an 8 s timeout, last known fix as fallback. **Data**: the catalog snapshot the app persisted (`EquipmentCatalog.snapshot(rebuildingIfStale: false)` — read-only, the widget never builds; hence the cache lives in the **App Group container** `Library/Caches/equipment-catalog.json`, `EquipmentCatalog.defaultCacheFileURL`) overlaid with the bundled seed for coordinates (so the iOS widget extension bundles the seed too — only the watch widget extension keeps the membership exception), then one targeted `equipment(for:)` status request. Before the app has ever built a catalog the seed previews names with unknown statuses. Tapping opens the app via `AppDeepLink.nearby` (`onOpenURL` in `ContentView`: locate + present the search). Apple recommends a separate extension for location-using widgets so the status widgets never trigger the location question — deliberately not done (one extension, smaller increment); revisit if the prompt turns out to show for the status widgets as well.

The `kind` strings are the widgets' identity — renaming a display name is safe, changing a `kind` orphans every already-placed instance. Display names deliberately do **not** repeat "Hissi": the gallery already groups tiles under the app name, so the one line each tile gets says what it shows.

The accessory families show the aggregate verdict only (`ElevatorSummary`, see below) and never rely on colour — the lock screen renders them in vibrant mode, so shape and words carry the status; rectangular adds the affected station as a third line, inline and circular name the app themselves (inline in its text, circular via VoiceOver), because nothing around them does. The home-screen families carry the mark (`WidgetMark`, `LogoMark` at caption height) as the tile's identity — no wordmark, the system chrome names the app — on the palette's ground (`hissiWidgetBackground()`), rows in the status pairs (`symbolColor`/`textColor`). Every unit is a single VoiceOver element (summary sentence / one sentence per row). `LiftEntry.relevance` (from `ElevatorSummary.relevanceScore`) ranks the widget inside a Smart Stack — on iOS it drives Smart Rotate only, **not** the gallery, whose ordering is system-controlled and has no API.

### Live Activity — the „Live-Status" (`Shared/LiveStatus.swift`, `HissiWidget/LiveStatusActivity.swift`)

The only **non-passive** surface: every other glanceable surface waits to be looked at, the live status is started by the user for a trip, lives on the lock screen and in the Dynamic Island, and **alerts** on a status change. Without a push server that `AlertConfiguration` (no notification permission needed) is the app's only way to reach someone whose phone is in a pocket — which is also why it fires on real transitions only.

Scope is **all favorites**: the same aggregate verdict as everywhere else (`ElevatorSummary`, FR13) plus the most urgent rows below it (`ElevatorRanking.byUrgency` in `Shared/`, extracted from the widget list so a broken elevator never falls off the row cap). Since iOS 27 the compact Dynamic Island presentation is also visible in landscape without room to grow — there the trailing text shrinks to `ElevatorSummary.minimalLabel` ("2" instead of "2 defekt"; `isDynamicIslandLimitedInWidth` environment, `#available`-guarded).

The split follows `ElevatorSummary`: **rules pure in `Shared/LiveStatus.swift`** (mode, `ContentState` = `LiveStatusState`, alert transitions, end rule — Foundation only, unit-tested in `HissiTests/Tests/LiveStatusTests.swift`), **ActivityKit only as a shell** (`Shared/LiveStatusAttributes.swift`), **plumbing in the app** (`Hissi/Services/LiveActivityController.swift`: start/update/end, re-adoption of a running activity after a cold start, `@Published mode` for the UI) and **presentation in the widget extension** (pinned to the dark scheme on the palette's dark ground, `liveStatusGround` — the Lock Screen renders activities dark regardless of wallpaper, and a light tint there comes out as an unreadable orange wash). ActivityKit code in `Shared/` **must** be `#if os(iOS) && canImport(ActivityKit)`-guarded — `Shared/` also compiles into the two watchOS targets and into the SwiftPM test package (macOS), and ActivityKit exists in neither. The stop button's `LiveActivityIntent` (`Shared/LiveStatusIntents.swift`) lives in `Shared/` for the opposite reason: the extension needs the type to build the button, the app is where `perform()` runs, and `Shared/` is the only place compiled into both.

Two end rules, chosen at start and fixed for the activity's lifetime (part of the static attributes): **`trip(endsAt:)`** for two hours (the countdown ticks without any update) and **`untilRepaired`** — only offered while something is broken — which ends as soon as nothing is. Both also end when the last favorite goes; iOS ends Live Activities after a few hours anyway, which the start UI (`Hissi/Views/LiveStatusSection.swift`, above the favorites list) says out loud. `NSSupportsLiveActivities` in `Hissi/Info.plist` is what makes `Activity.request()` work at all; starting needs the foreground (no push-to-start without APNs), updating from the background task does not.

watchOS 11 **mirrors the running activity into the watch's Smart Stack**; the widget opts into the `.small` activity family (`supplementalActivityFamilies`, iOS 18 — the reason the deployment target is 18: a `Widget` body can't branch on availability and the bundle builder has no `else`) and `LiveStatusWatchView` renders it like the watch's rectangular complication (`LogoMark` left — hence the mark lives in `Shared/` — verdict, station, checked/stale line, countdown; no end button, interactive elements don't run on the watch; VoiceOver speaks `spokenLabel`). The phone renders it and the watch shows it. Updates ride the existing refresh path (`ElevatorMonitorService.refresh()`, the background task) — there is no push server, so those are the only moments the live status learns anything, and that is made visible instead of hidden: every update carries a `staleDate` two live-status cycles out, past which the activity says "Status möglicherweise veraltet" (`context.isStale`) rather than presenting an old status as current. Alerts compare **per elevator id** against the previous favorites, not by counts (one breaking while another is repaired leaves the counts identical); a standing disruption never re-announces itself, and neither a newly favorited broken elevator nor a fall back to *unknown* (source failure) alerts.

### Watch app (`HissiWatch/`)

Separate Xcode target embedded into the iOS app. Sources auto-sync from `HissiWatch/` plus `Shared/`. The watch has **no favorites of its own** — it lives in a separate App Group container. `WatchSync` receives the favorites via `WCSession` application context, mirrors them into the watch's `ElevatorCache`, and reloads the complications; when nothing has been pushed yet, `WatchElevatorService` falls back to a self-fetch off that cache. Colours are the palette's dark values as constants in `WatchContentView.swift` (`watchSurface` for the rows, `watchTextSecondary`, `ElevatorStatus.watchColor` — the wrist is always dark, so nothing there relies on the catalog's appearance resolution). UI shows the elevators in a `.carousel` list (no empty-state placeholder — without favorites the list is just the nearby entry); tapping a row pushes a `TabView .verticalPage` pager. Above the favorites an "In der Nähe" row pushes `WatchNearbyView` — the one watch screen that is **not** a mirror: the watch locates itself (`LocationProvider`, authorization inherited from the phone app when paired) and runs the same `NearbyStations.nearest` over `EquipmentCatalog.shared` as the phone (the seed is bundled into the watch app for the coordinates), two-phase: snapshot first, then a targeted `equipment(for:)` refresh; on the very first use there is no snapshot, so it builds the catalog once (~30 s, rows up meanwhile) and re-derives the rows — the order holds because distances come from the seed either way (unit-tested). Tapping a station shows its elevators in the favorites' pager. The nearby complication reaches this screen via `AppDeepLink.nearby` (Shared; `widgetURL` → `onOpenURL`, root stack on a `NavigationPath` so the nearby screen can push station values of its own).

### Watch complications (`HissiWatchWidget/`)

Separate watchOS Widget Extension embedded into the watch app. Sources auto-sync from `HissiWatchWidget/` plus `Shared/` (minus the seed, via a membership exception). `@main` is a `WidgetBundle` with two complications, hero first: the status complication and **"In der Nähe"** (`NearbyComplication`, kind `HissiWatchNearby`) — a static launcher whose tap opens the watch app's nearby screen through `AppDeepLink.nearby`; a complication can't run a search itself, so it shows no data and never refreshes (`.never`). The status complication is listed in the picker as "Aufzug-Status" (the picker groups under the app name, so the display name says what it shows; the `kind` stays `HissiWatchWidget` — changing it would drop the complication off every face it is already on). Provides `.accessoryCircular` (status ring + status symbol), `.accessoryRectangular` (logo mark left, status symbol + status line in status colour, affected stations below — no wordmark, the mark is the identity), `.accessoryInline` (logo mark as a monochrome template + `shortLabel`) and `.accessoryCorner` (status word inside, a curved `Gauge` in the status colour along the bezel filled by `ElevatorSummary.affectedShare` — no words, no name). Rectangular doubles as the **Smart Stack** face on watchOS 10+ — that is why it carries the extra station line — and `LiftEntry.relevance` (from `ElevatorSummary.relevanceScore`: broken 100 / unknown 25 / else 0) is what makes the Smart Stack surface it when something is broken and leave it at baseline otherwise. Complications show the **aggregate status only** (OK / n defekt / ?) with no data-age display — freshness comes from the refresh cadence. Membership comes from the **mirrored `ElevatorCache`** (not favorites, which the watch can't read). An **empty mirror shows the app's mark** (`EmptyComplicationView`: circular and corner the logo alone, rectangular and inline the logo next to "Keine Favoriten") — no favorites and not-yet-synced are indistinguishable on the wrist and neither is actionable there; VoiceOver reads "Keine Lift-Favoriten" (`ElevatorSummary([]).spokenLabel`), synced or not — `awaitingSync` now only feeds the relevance score. The mark is `LogoMark` (`Shared/LogoMark.swift`, also drawn by the iOS widget extension in every home-screen family and the Live Activity): the icon's mark (frame, chevrons, dot — the small-size cut of `logo.svg`) drawn as shapes, because the extension has no asset catalog; its colours follow the ground (`HissiMarkFrame`/`HissiMarkAccent` pairs — lilac and green on light, cream and mint on dark; the watch targets hard-code the dark pair); the nearby complication uses it the same way (inline there keeps the location symbol). Tinted faces flatten it to the face's tint, and inline renders it as a monochrome template. Fetches live status and falls back to the cache on failure. One timeline entry per refresh; reloads after `RefreshInterval.minutes`.

### Aggregate verdict (`Shared/ElevatorSummary.swift`)

Every glanceable surface (lock screen, StandBy, complications, Smart Stack) reduces the favorites to one verdict before rendering: `noFavorites` / `broken` / `unknown` / `allWorking`, in that precedence (plus `awaitingSync`, watch-only: an empty mirror before the first sync, never derived from an elevator list), plus counts, `affectedStations` (broken first, deduplicated — the extra line the rectangular families have room for), the SF Symbol, the German labels (`label` full sentence, `shortLabel` compact, `identifiedLabel`/`identifiedShortLabel` prefixed with "Hissi:" for the iOS families that are otherwise anonymous, `spokenLabel` for the watch complications' VoiceOver — nothing on the face names the app and the system doesn't either, so the sentence names the subject instead: "2 Lifte außer Betrieb", "Alle Lifte in Betrieb", "Keine Lift-Favoriten"; the nearby complication says "Lifte in der Nähe"), `affectedShare` (a gauge value: full on an all-clear, else the broken+unknown fraction) and `relevanceScore`. Pure and platform-free (Foundation only), unit-tested in `HissiTests/Tests/ElevatorSummaryTests.swift`, so both widget extensions speak one vocabulary. "No favorites" is a case of its own — with nothing to monitor, "Alle in Betrieb" would be a false all-clear.
